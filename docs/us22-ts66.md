## Estado y responsabilidad

Esta entrega prepara la estructura para definir reglas de clasificación. **Los indicadores,
fuentes, rangos, umbrales y criterios financieros no están aprobados.** No hay política
productiva configurada, motor ejecutable ni entidades clasificadas.

El usuario confirmó que TS-67 (motor), TS-68 (integración JSON) y TS-69 (pruebas de
clasificación) deben quedar al equipo. Por ello no se añaden RiskClassifier,

## Contratos propuestos

Los archivos de `backend/src/risk/domain/` son independientes del motor de rentabilidad:

- `RiskLevel.ts`: VERDE, AMARILLO y ROJO. La ausencia de clasificación se representará
  mediante `RiskLevel | null`, nunca mediante un cuarto nivel ni VERDE por defecto.
- `SolvencyIndicators.ts`: identificador estable de entidad y mapa de indicadores.
  Cada indicador incluye valor Decimal, unidad, URL de fuente y fecha de observación.
  Los nombres son configurables: el backlog no define indicadores concretos.
- `RiskClassificationRules.ts`: requisitos de datos por indicador, versión, aprobación y
  condiciones de cada nivel. Los límites y umbrales son Decimal. No hay constantes numéricas
  de riesgo, una política predeterminada ni datos de solvencia de ejemplo en producción.

Las interfaces TypeScript describen el contrato; no validan datos externos en tiempo de
ejecución ni certifican una fuente. El adaptador de datos y el futuro motor deben comprobarlo.
No basta con rellenar sourceUrl o approval para considerar verificada una fuente o aprobada
una política: esos metadatos deben provenir del proceso de revisión del equipo.

## Semántica propuesta para acordar con TS-67

1. Sin política o con `approval: null`, el futuro clasificador devuelve null.
2. Cada indicador requerido debe tener una observación de la entidad correcta, fuente
   verificable, unidad compatible, fecha válida y antigüedad dentro de maxAgeDays.
3. Los valores y umbrales deben ser decimales finitos. Se rechazan NaN, Infinity,
   texto mal formado, fechas futuras y valores fuera del rango aprobado del indicador.
   No se aplica una prohibición genérica de valores negativos: depende de su definición.
4. Una política válida requiere versión y evidencia de aprobación, nombres de requisitos
   únicos, lista no vacía, minimum <= maximum y maxAgeDays entero no negativo.
5. Cada uno de los tres niveles necesita al menos una condición; una lista vacía nunca
   significa coincidencia automática. Toda condición referencia un indicador requerido y
   usa un operador admitido. LT y GT son estrictos; LTE y GTE incluyen el límite.
6. Dentro de un nivel se propone AND: todas sus condiciones deben cumplirse.
   Exactamente un nivel debe coincidir. Si no coincide ninguno o hay solapamiento, devolver
   null e informar del problema de configuración, sin priorizar colores arbitrariamente.
7. Si faltan datos o no son válidos, devolver null. Nunca sustituirlos por cero ni usar
   TEA, rentabilidad, nombre de entidad, azar o monto mínimo para asignar riesgo.

Esta semántica es una propuesta técnica para coordinar, no una aprobación de una metodología
financiera. Si el equipo necesita grupos OR, ponderaciones o prioridades, debe acordarlos
antes de ampliar el contrato. No se añadieron esos mecanismos anticipadamente.

## Integración futura y JSON

TS-67 implementará la evaluación sobre estos contratos y decidirá si necesita una capa de
coordinación. TS-68 deberá asociar datos a la entidad mediante identificador estable;
FinancialProduct actualmente solo tiene id de producto y nombre visible. No debe resolver
esa asociación usando el nombre como identificador ni añadir indicadores ficticios al catálogo.

**Contrato propuesto, todavía no implementado por esta rama:** preservar los campos
existentes de la respuesta y agregar `riskLevel: "VERDE" | "AMARILLO" | "ROJO" | null`.
Por ejemplo, un fragmento de respuesta sin clasificación disponible sería:

```json
{"riskLevel": null}
```

El endpoint actualmente NO devuelve riskLevel. El fragmento anterior no es una respuesta
observada ni una prueba de integración. TS-68 es quien debe incorporar y serializar el campo.

Coordinar con Sprint 1: US12 añade `minimumAmount` como sexto argumento de SimulationResult
y campo JSON decimal. TS-68 debe conservarlo, conservar los otros campos y no cambiar
las fórmulas, las modalidades de pago, el filtro de productos o el orden de resultados.
La rama TS-66 parte de main y no contiene esos cambios de US12.

US23 consumirá el campo cuando TS-68 esté disponible. Debe tratar null como información
no disponible; la decisión de presentación pertenece a su responsable. Esta entrega no
contiene iconos, CSS, colores, modales ni descripciones de riesgo en React.

## Plan de pruebas para TS-69

Cuando el equipo implemente el motor, usar indicadores y umbrales **sintéticos, exclusivamente
en tests**, identificados como ejemplos técnicos sin validez financiera:

- Casos VERDE, AMARILLO y ROJO; igualdad en los límites LT/LTE/GT/GTE.
- Varios indicadores con AND; rangos vacíos, huecos y solapamientos entre niveles.
- Indicadores faltantes, unidad incorrecta, fuente no verificada y entidad equivocada.
- Política ausente o sin aprobación, nombres duplicados y condiciones desconocidas.
- NaN, Infinity, valores fuera del rango, observaciones caducadas y fechas inválidas/futuras.
- Persistencia del resto del JSON y serialización explícita de null en HTTP.
- Regresión de ambas modalidades, precisión decimal, orden y compatibilidad con US12.

No se añadieron tests de clasificación: no existe un clasificador en el alcance autorizado.
La validación ejecutada sobre esta rama comprende las 55 pruebas previas del backend,
compilación de backend/frontend y ESLint de ambos. La rama independiente de main no tiene
script de tests frontend; las 22 pruebas de US06/US12 están en su propia rama.
